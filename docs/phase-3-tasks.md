# Phase 3 — The CRM surface

Phase 2 made every import decision writable, reviewable and reversible, proven by hash. Phase 3 is the comfortable half: households and their names, pledges, soft credits, campaign roll-ups, segments as data, acknowledgement letters, Marcus's gift list, the constituent page, and the import and review pages that D-50 (P-6) deferred. It is the **last P0 phase**. The risk now is scope creep (PRD Risks), so every task names its oracle number or its fixture, and anything not on this list is a seam.

Order: oracle and data first, then the pure derivations (households, roll-ups, segments), then the write paths (gift correction, pledges, soft credits, letters), then the pages, then gate wiring. Each task writes the failing test first, against `housefile_test` or a committed fixture. `src/matching/` stays untouched. New write paths live in `src/commit/` so `write:lint` keeps meaning "only `src/commit/` writes"; pages call server actions that call `src/commit/`, never Prisma directly.

**Written at the Phase 2 gate, 2026-10-22.** Gate output (local, one run, stopped on first failure, none failed): `typecheck` clean, `fixtures:check` OK, `model:lint` OK (40312dfe…), `money:lint` OK, `write:lint` OK, `import:eval` A 259/55/71 · P 1.0 · R 0.9464, B 166/33/37 · P 1.0 · R 0.9548, drift 0 rows, labels 30 / 30, `foundation:drift` clean against v1.3.0, `npm test` 49 files / **434 / 434**, `phase2:proof:test` OK (undo B `2c035193…` == beforeHash, undo A `7d3bd174…` == beforeHash, both unmerge snapshots equal). | P-10 | **Segments are new code, not a Pulseboard port.** Checked 2026-10-22: Pulseboard's `src/` has rollups, funnels and retention but no segment definitions, and its rollups are *stored* day tables (DELETE + INSERT on a watermark), the opposite of D-27. A `SegmentRun` stores the member business ids, count, `asOf`, definition hash and a hash of the member list, as a reproducible snapshot, never read back as truth. | The overlap doc's "ported, not redesigned" was written without the donor's source (it says so); the lineage line in D-33 should not claim a port that did not happen | Port Pulseboard's stored rollup tables for campaigns (fast, but a second source of truth next to append-only gifts) |
| P-11 | **Giving year = calendar year, and every segment and roll-up takes an explicit `asOf`** (default 2026-10-14, as D-37). | P-13 | **Pledges and pledge payments enter the effective-state hash** (D-11 extended): each active pledge by `pledgeRef` with its schedule; a payment is a gift whose `pledgeRef` is part of its hashed fields. Household *names* are derived at read time and not hashed. | Undo and unmerge proofs keep covering everything a person can see on the constituent page | Leave pledges out of the hash (then a pledge written by a batch cannot be proven undone) |
| P-14 | **Gift correction by hand:** `correctGift(giftRef, change, reason, actor)` and `voidGift(giftRef, reason, actor)` write a superseding row (D-6), gated by `results.write` (D-60), audited. | P-15 | **Pages are server components plus server actions over the existing `src/commit/` functions, one Playwright spec per page, run against the production build on 5900 (house rule).** No client-side state library; tables are plain HTML with links; the review pair page shows both records, reasons and points, and the four actions. | Phase 3's lesson is the data surface, not a design system; the template's `src/core/ui` covers layout | A component library (new dependency, needs asking) |
