# Phase 2 — Commit, review, merge, undo

Phase 1 proved the pipeline decides what the oracle decides, in memory. Phase 2 makes those decisions **writable, reviewable and reversible**, and proves each reversal with a hash. Input is still the frozen fixtures: the CRM fixture is seeded into Postgres once, and the two import files are previewed, committed, reviewed and undone against it. No CRM surface beyond what the review queue needs (households display, roll-ups, segments, letters and the constituent page are Phase 3).

Order is CLAUDE.md's TDD order. Every task writes the failing test first against `housefile_test`. `src/matching/` stays pure and untouched: anything that needs the database or a clock (pair memory, tied candidates, S6) lives in `src/import/` or a new `src/commit/`.

## Proposals (reviewed 2026-10-19: P-1, P-2, P-6, P-7 decided by Shane as written; P-3..P-5 defaults in force — D-45..D-51)

| # | Proposal | Why | Alternative |
|---|---|---|---|
| P-1 | **Aliases, alternates and the household link live inside `ConstituentVersion`** (JSON arrays plus `householdId`), not in their own tables. Every write to a constituent, including a household link, is a new version tagged with its writer. | Undo and unmerge become one operation: write a version equal to the earlier one. Effective state is "latest version per constituent", one query. D-7 and D-8 are both satisfied (the version row *is* the tagged link row). Cuts three append-only tables and their triggers. | Separate `Alias`, `Alternate`, `HouseholdLink` tables, each append-only with retire rows; undo must reverse each table on its own |
| P-2 | **Every merge writes a `MergeEvent`**, including an import row merging into an existing constituent (auto or reviewed), with `kind = ROW_INTO_CONSTITUENT` or `CONSTITUENT_INTO_CONSTITUENT`. Unmerging a row merge splits the row back out as a new constituent with its gift. | Non-negotiable 2 says every merge is undoable. It also gives Dana a way to fix a wrong *auto*-merge without undoing the whole batch. | MergeEvent only for two-constituent merges; a wrong auto-merge can be fixed only by undoing its batch |
| P-3 | **ImportBatch is an immutable header written at preview time** (raw bytes, content hash, map, parsed rows, plan, `planHash`, `beforeHash`). Status is derived from append-only `ImportBatchEvent` rows (`COMMITTED`, `UNDONE`, `UNDO_FAILED` with both hashes). `STATE_MOVED` means a **new** batch is previewed; the old one stays as written. | D-6 puts ImportBatch under the append-only triggers, so it cannot carry a mutable status column. | A mutable `status` column exempted from the trigger |
| P-4 | **Gifts carry a stable business id (`giftRef`)** across supersession. A gift moved by a merge or unmerge is a superseding row with the same `giftRef` and a new constituent; the effective-state hash uses `giftRef`, never the row id. | Without it, unmerge cannot hash equal: the restored gift would be a new row with a new id. | Hash on content only; breaks when two gifts share date, cents and constituent |
| P-5 | **Constituent-into-constituent survivorship** (S6 review, P-2): the record with the earlier `created_at` is the survivor for S3 (names, suffix, DOB); S1/S2 apply field by field as for a row. | The brief's "existing wins" has no meaning when both are existing. | Reviewer picks the survivor on the pair page |
| P-6 | **No import or review pages in Phase 2.** The review actions are server actions with a CLI (`review:list`, `review:decide`); the pages land with the Phase 3 CRM surface. | Phase 2's risk is the write path and its proofs, not the screens; one UI pass in Phase 3 instead of two. | A bare import page and review pair page at the end of Phase 2 (task 2.11b), one Playwright spec each |
| P-7 | **B-after-A on the database has no oracle.** In memory, the oracle enriches the CRM with A's MERGE rows only (D-34); on the database A also writes NEW constituents and leaves 55 review rows open, so B's decisions *will* differ from `decisions_b.csv`. Phase 2 proves the DB path two ways instead: A previewed against the seeded org reproduces `decisions_a.csv` with 0 drift, and B against the seeded org reproduces the Phase 1 "B alone" result (the 10 rows named in D-34). `import:eval` stays the in-memory gate. | An expected value invented for B-after-A would be a number nobody derived. | Regenerate a `decisions_b_after_a_committed.csv` from an extended oracle (oracle work, brief and §12 hashes change) |

## Tasks

- [x] **2.1 Schema and triggers.** Clone-owned `prisma/schema/housefile.prisma`: `Constituent` (org, business id, `kind = PERSON`), `ConstituentVersion` (full field set incl. per-field `asOf` and source, aliases, alternates, `householdId`, `status ACTIVE | RETIRED`, writer: exactly one of `importBatchId` / `mergeEventId` / `reviewDecisionId` / `userId`), `Household`, `Fund` / `Campaign` / `Appeal` (minimal, codes from `crm_gifts.csv`), `Gift` (`giftRef`, `amountCents Int`, date, fund, appeal, type, `externalRef`, `supersedesGiftId`, `status ACTIVE | VOIDED`, `reason`, `importBatchId`), `SoftCredit` (table only; Phase 3 writes it), `ImportBatch`, `ImportBatchEvent`, `ReviewItem`, `ReviewDecision`, `MergeEvent`. One clone migration with hand-written SQL triggers rejecting UPDATE and DELETE on `ConstituentVersion`, `Gift`, `ImportBatch`, `ImportBatchEvent`, `ReviewDecision`, `MergeEvent` (pattern ported from the foundation's `AuditEvent_append_only`; TRUNCATE stays allowed for tests). Every row carries `orgId`. *Acceptance:* `db:migrate` and `db:migrate:test` apply, schema diff empty, `foundation:drift` clean; one test per table proves UPDATE and DELETE raise; `money:lint` covers `amountCents`.
- [ ] **2.2 Effective state and seed.** Pure `effectiveStateHash(state)` (D-11 shape: every ACTIVE constituent's latest version incl. aliases, alternates, household; every active gift by `giftRef`; soft credits; sorted by business id; no row ids, `createdAt`, batch ids or audit rows) replaces Phase 1's `stateHash`, so the dry-run and the database hash the same shape. `loadEffectiveState(tx, orgId)` reads it from Postgres. `db:seed:fixtures` loads `crm_constituents.csv` and `crm_gifts.csv` into one org as version 1 and active gifts; refuses when `NODE_ENV=production`; idempotent. *Acceptance:* the hash of the seeded org equals the hash of the fixture loaded in memory; a second seed writes 0 rows; the change to the dry-run's `beforeHash` value is recorded in a D-entry with old and new hashes (it is a snapshot of our own code, not an oracle value).
- [ ] **2.3 Preview persisted, `beforeHash`.** `previewBatch(orgId, bytes, map, asOf)` runs the Phase 1 pipeline against `loadEffectiveState`, then writes **one** `ImportBatch` row (raw bytes, content hash, encoding, map with `extras`, parsed and normalized rows with rule traces, the plan, `planHash`, `beforeHash`) and nothing else. CLI `import:preview -- --file --map`. *Acceptance:* `import_a.csv` against the seeded org reproduces `decisions_a.csv` with 0 drift and the Phase 1 dry-run report byte for byte (except `beforeHash`, per 2.2); `import_b.csv` against the seeded org reproduces the Phase 1 "B alone" result (P-7); the plan rebuilt from the stored batch alone equals the stored plan (D-10); row counts in every other table are unchanged.
- [ ] **2.4 Commit.** `commitBatch(batchId)`: the only input is a batch id (no exported function takes parsed rows and writes). Recompute `effectiveStateHash`; differs from `beforeHash` → `STATE_MOVED`, nothing written. Recompute `planHash`; differs → `PLAN_TAMPERED`. One transaction writes exactly the plan: NEW rows → constituent + version 1; MERGE rows → survivorship version + `MergeEvent` (P-2) + gift; gifts with `DUP_GIFT` / `DUP_GIFT_IN_FILE` skipped as listed; REVIEW pairs → `ReviewItem` (all tied candidates, D-35; S6 `EXISTING_PAIR`); every row tagged with the batch; `ImportBatchEvent COMMITTED`. Idempotent on (batch id, plan hash). CLI `import:commit -- --batch`. *Acceptance:* after committing A, the written rows equal the plan count for count (constituents created, rows merged, gifts added and skipped, review items: each equal to the dry-run report's total for A); a second commit writes 0 rows; a constituent changed between preview and commit → `STATE_MOVED` with 0 rows written.
- [ ] **2.5 Review actions.** `MERGE`, `KEEP_SEPARATE`, `SAME_HOUSEHOLD`, `DEFER` on a `ReviewItem` (D-22): reason required for MERGE and KEEP_SEPARATE; who and when on `ReviewDecision` and in the foundation audit log; permission-checked by role. MERGE writes as 2.4 would have; KEEP_SEPARATE creates the row as a new constituent and records pair memory (the identifiers that agreed); SAME_HOUSEHOLD creates the constituent and links it to the target's household, creating one if needed (S5); DEFER leaves the item open. Every write tagged with the item's batch (D-14). Batch is `COMPLETE` when no item is open (derived). A later import does not re-queue a KEEP_SEPARATE pair unless an identifier that did not agree before now agrees. CLI `review:list`, `review:decide`. *Acceptance:* one test per action; MERGE and KEEP_SEPARATE without a reason are refused; the pair-memory test re-imports the same row (not queued) and a row with a new matching phone (queued).
- [ ] **2.6 Survivorship and `MergeEvent`.** S1–S6 (brief §8) on the database path, P-5 for constituent-into-constituent. `MergeEvent` stores both records' effective state, the survivorship choice per field with its rule, the gift and soft-credit refs moved, who and why. Gifts move by superseding rows with the same `giftRef` (P-4). *Acceptance:* GA-02 accepted leaves the import's spelling as an alias and the losing email as an alternate with source and `asOf`; S2 newer-`asOf` test both ways; suffix and DOB never change (S3); a GA-09-style tie offers both candidates; the field changes on the database equal the dry-run report's field changes for file A.
- [ ] **2.7 Unmerge.** `unmerge(mergeEventId)` re-creates the loser from its snapshot as a new version (a row merge re-creates the row's constituent, P-2), reverts the survivor to its snapshot, moves gifts and soft credits back by superseding rows. Refused with `UNMERGE_BLOCKED` when a later `MergeEvent` touched either record. *Acceptance:* each record's effective-state hash equals its snapshot hash after unmerge, for a row merge and a constituent-into-constituent merge; the blocked case writes 0 rows.
- [ ] **2.8 Undo a batch.** `undoBatch(batchId)` (brief §8, D-13): created constituents → RETIRED version (O-7); field changes → a version equal to the pre-batch one; gifts → `VOIDED` superseding rows with reason `BATCH_UNDONE`; merges (including review MERGEs under the batch) → unmerge; household links → version without the link. Then `effectiveStateHash == beforeHash` inside the transaction; mismatch rolls back and writes `ImportBatchEvent UNDO_FAILED` with both hashes outside it. Refused with `UNDO_BLOCKED_BY_LATER_BATCH` when a later batch wrote to a touched constituent; reverse order only. CLI `import:undo -- --batch`. *Acceptance:* the hash proof passes on file A, on file B, on A-then-B undone in reverse order, and on a hand-built batch with an auto-merge, a reviewed MERGE, a SAME_HOUSEHOLD and an S3 name-change alias; the A-then-B case refuses undoing A first; an injected fault makes `UNDO_FAILED` with both hashes and leaves the state unchanged.
- [ ] **2.9 Tamper tests.** With the triggers disabled in a test transaction, change one gift's cents, one version's email and one stored plan: commit refuses (`STATE_MOVED`, `PLAN_TAMPERED`) and undo writes `UNDO_FAILED`. With the triggers on, UPDATE and DELETE are refused on all six tables. A test fails if any module under `src/` other than `src/commit/` writes to the Phase 2 tables (import-graph check, like `model:lint`'s grep). *Acceptance:* each tamper names its code; the import-graph check is red on a planted violation, then green.
- [ ] **2.10 Gate wiring.** CI: the `ci` job runs the new integration tests against its Postgres; a `phase2-proof` step runs seed → preview → commit → undo for both files and prints both hashes. `docs/EVAL.md` gains a Phase 2 section: the undo and unmerge proofs as commands with their printed hashes, review load as rows and as a share. *Acceptance:* a red run (one survivorship rule changed so undo cannot restore) and a green run linked in `NEXT.md`.

**Exit criteria:** every write path starts from a stored preview (2.3, 2.4, 2.9); commit of A and B writes exactly their plans; each review action works and is audited, and KEEP_SEPARATE is remembered; unmerge restores both records' snapshot hashes; `undoBatch` restores `beforeHash` on A, B, A-then-B and the hand-built batch, and refuses out-of-order undo; UPDATE/DELETE refused on all append-only tables; Phase 1 gate still green (`import:eval` drift 0, `fixtures:check`, `model:lint`, `money:lint`); CI enforces it.
