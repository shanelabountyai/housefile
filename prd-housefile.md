# PRD: Housefile — Nonprofit Donor Management with Messy Import

**Sample business:** "Housefile," the donor database of a small community foundation (about 400 synthetic constituents, four years of giving, one messy donor file arriving after a gala and one after a peer-to-peer run)
**Build log:** #22 Nonprofit / Donor Management, main track. Chips: CRM · campaigns · segmentation · receipts · CSV import · dedupe + entity resolution
**Status:** Draft v1.1 — product-owner + CRM data-quality review folded in (see `docs/decisions.md` §Review log)
**Learning objectives:** a messy spreadsheet becomes trustworthy CRM records without a single blind write — column mapping, row-level validation with reasons, normalization, candidate blocking, explainable match scoring with three outcomes (merge / review / new), a human review queue, survivorship, a dry-run preview of every write, and an undo of a whole import batch proven by a hash of the before-state; all measured against an answer key as precision, recall and review load

**Positioning note:** the CRM half of this project (contacts, gifts, campaigns, segments, acknowledgement letters) is the part of the portfolio closest to Shane's day job, so it is built to be evaluated expertly, not to teach. The lesson is the import. Nothing else in the portfolio takes a file whose rows *might* be people already on record and has to decide, explain, preview and be able to take it back. `docs/portfolio-overlap.md` lists what is ported, from where, and what is new.

The name: a nonprofit's own donor list is its "house file" in direct-response fundraising.

`docs/decisions.md` outranks this document wherever they differ.

## ⚠️ Scope Honesty (read first)

Learning project, synthetic data only. Every person, address, email, phone and gift is generated by `tools/build_fixtures.py` from a seed; phone numbers sit in the 555-01xx reserved block and emails use `example.*` domains. No real donor file is ever loaded. Acknowledgement letters are *sample letters*: US charities have written-acknowledgment rules (IRS Publication 1771; see `docs/domain-brief.md` §2) and this project does not claim to satisfy them. No payment processing, no email sending, no wealth screening, no tax advice. The matcher is a heuristic: screens and write-ups report what was measured against the answer key, never "accurate" without a number. Banner verbatim in the README.

## Problem Statement

A development director gets a spreadsheet after every event: a gala platform export, a peer-to-peer run's donor list, a board member's "people I know" sheet. Some of those people are already in the database under a nickname, a maiden name, an old address, or a shared family email. Some are new. Some are two different people with the same name in the same city, or a father and son at one address. Loading the file is a choice between two failures: import everything and create duplicates that split giving history and send two thank-you letters, or merge aggressively and silently glue two people into one record, which is far harder to notice and far harder to undo. Most small shops do this in Excel by eye, once, and live with the result.

Housefile treats the import as a pipeline with a decision at every row, each decision explained in terms a volunteer can check ("same email, same address, first name Bob is a nickname for Robert"), each uncertain decision sent to a person, and the whole batch previewed before anything is written and reversible after. The builder lesson: entity resolution is not a clever similarity function. It is normalization you can state, a scoring model you can read, thresholds you measured, a review queue sized for a human, and an undo you can prove.

## Goals

1. **Nothing is written without a preview.** Every import shows exactly which records would be created, which fields would change on which existing records, which gifts would be added, and which rows would be rejected or sent to review, before the commit button exists.
2. **Every match decision is explainable and deterministic.** The same file against the same database gives the same decisions, and every decision lists the reasons and points that produced it.
3. **Wrong merges are the expensive error, and the model is tuned that way.** Target: auto-merge pair precision ≥ 0.99 on the frozen fixtures, measured and printed by `import:eval`, with review load reported alongside so the precision isn't bought by sending everything to review.
4. **A merge and an import batch are both undoable**, and undo is proven: the effective-state hash after undo equals the hash taken before commit.
5. **Gifts are money, append-only, in integer cents.** A correction is a superseding row, never an UPDATE.
6. **(Builder goal)** Know, in numbers, what the matcher does and does not catch, and say so.

## Non-Goals

- **Payment processing, online donation forms, recurring-gift collection.** Gifts enter by import or by hand.
- **Sending email or mail.** Acknowledgement letters are rendered and queued to the notifications outbox; nothing leaves.
- **Wealth screening, prospect research, NCOA/address-verification APIs, email-verification services.** Normalization is rule-based and offline.
- **Tax compliance.** Letters are samples. The $250 / $75 figures are cited, not implemented as rules.
- **Real-person data of any kind, including "anonymized" exports.**
- **Volunteers, events, ticketing, memberships, grants, pledge reminders, moves management.** Seams only.
- **Machine-learned matching in Phase 1–3.** The matcher is a hand-set additive model. An LLM review-assist is a Phase 4 *experiment* with a cost cap (O-1).
- **A general rules engine for scoring.** Features and points are a closed table in `matching/model.v1.json`; a new feature needs a decision and a golden pair.
- **Multi-tenant SaaS billing, public API, webhooks.** Projects 19 and 20.

## Personas

- **Dana, development director** — owns the relationships. Works the review queue after an import, approves merges she can defend, wants to see "why" in one line per pair, and signs the acknowledgement letters.
- **Priya, data/ops volunteer** — arrives with the spreadsheet. Maps columns, reads the validation report, fixes what she can in the file, re-uploads, commits, and needs undo when she realizes the file was last quarter's.
- **Marcus, finance** — reconciles gifts to the bank deposit. Needs gift totals by date, fund and campaign to tie out to the cent, and needs to see that a corrected gift is a superseding row with a reason, not a changed number.

## Requirements — Must-Have (P0)

**P0-1: Constituents, households, gifts (the CRM floor)**
- [ ] `Constituent` (person) with name parts (first, middle, last, suffix, preferred/nickname), one primary email, phone and address, optional DOB, aliases (prior names), alternate emails/phones/addresses with `asOf` and `source`; `Household` grouping constituents at one address with a derived household name; `Fund`, `Campaign`, `Appeal` (brief §2)
- [ ] `Gift` with `amountCents` (integer), date, fund, appeal (→ campaign), type (`GIFT`, `PLEDGE_PAYMENT`, `IN_KIND`), `externalRef`, `importBatchId`, optional `pledgeId`; `SoftCredit` rows; **append-only** — a correction is a new gift row with `supersedesGiftId` and a reason; "voided" is derived (D-6)
- [ ] `Pledge` with schedule as data; balance derived from payments; no scheduler
- [ ] Every table clone-owned under its own Prisma schema file; immutability triggers as hand-written SQL

**P0-2: Import pipeline — parse, map, validate** *(core learning artifact #1)*
- [ ] Reads CSV with BOM, UTF-8 or cp1252 (recorded), CRLF or LF, quoted fields, extra and renamed columns; the raw bytes and parsed rows are stored on the `ImportBatch` with a content hash (D-10)
- [ ] Column mapping: the mapper proposes a map from header synonyms (brief §4), the user confirms or corrects, and the map is saved per source for reuse; unmapped columns are kept as `extras` JSON and never dropped silently
- [ ] Normalization N1–N9 (brief §5) applied per row; the normalized value and the rule that fired are both stored
- [ ] Validation produces, per row, `OK`, `WARN:<code>` or `REJECT:<code>` with the closed code set in brief §4; a rejected row never reaches matching; totals by code appear in the preview
- [ ] Fixture files `import_a.csv` and `import_b.csv` parse with zero crashes; `expected_validation` in the answer keys matches for every row

**P0-3: Matcher — blocking, scoring, decision** *(core learning artifact #2)*
- [ ] Pure module `src/matching/`: no database, clock, randomness or network; input is normalized records, output is `{score, reasons[], flags[], decision}`
- [ ] Blocking keys B1–B5 (brief §6); a pair is scored only when it shares a key; the count of pairs compared is reported
- [ ] Scoring model exactly brief §7 (`matching/model.v1.json`, content-hashed): features, points, Jaro-Winkler and Soundex as specified, thresholds `MERGE ≥ 70`, `REVIEW ≥ 45`, the suffix hard block, the first-name and DOB conflict caps, the identifier floor, the name-change floor, household-candidate flags
- [ ] Decisions are symmetric in argument order and deterministic; a test asserts both on the GA pairs
- [ ] Rows are resolved in file order against the existing records plus rows already accepted in this batch; a merged row's identifiers enrich its target for later rows (S1 within batch)
- [ ] `tools/golden_answers.py` GA-01..GA-20 and GN-01..GN-20 reproduced exactly by the TypeScript matcher

**P0-4: Dry-run preview and commit** *(core learning artifact #3)*
- [ ] Preview = the full list of proposed writes: constituents to create, field changes per existing constituent (old → new, survivorship rule that chose it), gifts to add, gifts skipped as duplicates with reason, rows rejected with reason, pairs sent to review; grouped and counted; downloadable as CSV
- [ ] `beforeHash` = canonical hash of the org's effective state (D-11) computed and stored on the batch at preview time; a commit whose recomputed before-hash differs from the stored one is refused (`STATE_MOVED`) and the preview is rebuilt
- [ ] Commit writes exactly the previewed changes in one transaction, every row tagged `importBatchId`; reviewed pairs are written only after their review decision; a batch with open reviews can commit the rest and leave the reviews open (D-14)
- [ ] Idempotent: committing the same batch twice writes nothing the second time

**P0-5: Review queue and merge** *(core learning artifact #4)*
- [ ] One `ReviewItem` per pair in the review band, showing both records side by side, the reasons and points, and the flags; actions: `MERGE`, `KEEP_SEPARATE`, `SAME_HOUSEHOLD` (links without merging), `DEFER`; who, when and a reason are audited
- [ ] Survivorship S1–S6 (brief §8) chooses field values on merge; every losing value is kept as an alias/alternate with its source; a merge writes a `MergeEvent` holding the full effective state of both records and the list of gifts and soft credits moved
- [ ] `unmerge(mergeEventId)` restores both records exactly (asserted by comparing the effective-state hash of each to the snapshot) and moves gifts back; refused if a later merge touched either record (`UNMERGE_BLOCKED`)
- [ ] Existing-to-existing merges proposed by an import (two CRM records both match one row) are never automatic (S6)

**P0-6: Undo an import batch** *(core learning artifact #5)*
- [ ] `undoBatch(batchId)` reverses every write the batch made as compensating rows: created constituents retired, field changes reverted to the pre-batch version, gifts voided by superseding rows, merges unmerged, household links removed; nothing is deleted
- [ ] After undo the effective-state hash equals `beforeHash`; the test proves it on both fixture files and on a hand-built batch that includes merges and a name-change survivorship
- [ ] Undo is refused when a later batch touched any of the same constituents (`UNDO_BLOCKED_BY_LATER_BATCH`); batches undo in reverse order only

**P0-7: Evaluation** *(the measured claim)*
- [ ] `npm run import:eval` runs the matcher over `fixtures/import_a.csv` and `import_b.csv` against `fixtures/crm_constituents.csv` and prints, per file: rows, rejected, rows merged / reviewed / new, pairs compared, auto-merge pairs, auto-merge wrong, true pairs below review, true pairs not blocked, review pairs and how many are true, **pair precision**, **pair recall**, and the expected-link × decision confusion table — the same fields and the same numbers as `tools/reference_matcher.py`
- [ ] Per-pair decisions match `fixtures/decisions_a.csv` and `decisions_b.csv` (written by the reference matcher) exactly; CI fails on any drift
- [ ] Hand-labeled set: Shane labels 30 review-band pairs (Phase 1 task 1.9); the eval prints agreement between his labels and the answer key, and the share he would have merged that the model kept in review
- [ ] Targets (stated as targets, not results): pair precision ≥ 0.99; pair recall ≥ 0.90; rows in review ≤ 20% of rows. Measured values go in `docs/EVAL.md` with the fixture hash

**P0-8: Campaigns, segments, acknowledgement letters**
- [ ] Campaign → appeal → gift roll-ups: raised, gift count, donor count, average gift, by fund; all integer cents
- [ ] Segments as data (closed vocabulary, D-16): filters on constituent fields and giving aggregates (total in window, last gift date, gift count, LYBUNT/SYBUNT, household vs individual); a segment is a saved definition plus a reproducible materialized list with its count and run time
- [ ] Acknowledgement letter per gift: rendered from a template with the gift date, amount, fund and the sample "no goods or services" sentence, queued to the notifications outbox as `QUEUED`, never sent; a gift superseded after its letter was queued raises `LETTER_STALE`; letters for a household's gifts can be combined into one
- [ ] Letter copy carries the sample-letter banner; no compliance wording beyond the cited note

**P0-9: Views**
- [ ] **Import:** upload → mapping → validation report → preview → commit → batch page (what was written, undo button with its blocked/unblocked state)
- [ ] **Review queue:** list, pair page with reasons, actions
- [ ] **Constituent:** record with aliases, household, giving history incl. superseded rows shown struck through with reason, merge history with unmerge
- [ ] **Campaign and segment pages**, **gift list** for Marcus with totals by date/fund that tie to the cent

## Phasing

1. **Pipeline + matcher + eval, no writes.** Parse, map, normalize, validate, block, score, decide; preview rendered as a report; `import:eval` reproducing the reference matcher; GA/GN goldens in TypeScript; the 30 hand labels. No commit, no review actions, no Prisma models for constituents or gifts yet; the CRM fixture is loaded read-only in memory.
2. **Commit, review, merge, undo.** Append-only schema with triggers, `ImportBatch` with `beforeHash`, commit, review queue with the four actions, survivorship, `MergeEvent` and unmerge, `undoBatch` with the hash proof, tamper tests.
3. **The CRM surface.** Households, pledges, soft credits, campaign roll-ups, segments as data, acknowledgement letters to the outbox, Marcus's gift list, constituent page with history.
4. **LLM review-assist experiment (optional, O-1).** Same review-band pairs, model suggests a decision with a one-line justification, compared against the answer key and against Shane's labels, cost capped and logged. Reported as numbers; the deterministic matcher stays the product path unless the experiment shows a measured gain.

## Risks

- **Oracle optimism.** The reference matcher scores 1.000 precision on defects the same author designed. Mitigation: Shane's hand labels; a documented list of defect types *not* generated (brief §3); a second messy file written by hand in Phase 3 (P1).
- **Survivorship arguments.** Whose address wins is a policy, not a fact. Mitigation: S-rules are data with a decision each, every losing value is kept.
- **Undo across batches.** Reverting a field change after a later batch changed it again is ambiguous. Mitigation: refuse (D-15), reverse order only.
- **Scope creep into the CRM.** It is the comfortable half. Mitigation: Phase 3 is the last P0 phase and its task list is written only at the Phase 2 gate.
- **Shared-email households.** The identifier floor sends every spouse pair to review; on a file of mostly couples the review load could exceed 20%. Mitigation: measured on the fixture (13–15% of rows); `SAME_HOUSEHOLD` is a one-click review action; `KEEP_SEPARATE` is remembered so the same couple is not re-queued every month (D-22).
